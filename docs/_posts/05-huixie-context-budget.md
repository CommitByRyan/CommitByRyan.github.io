# 05 单章上下文 12k 硬预算

> 从 87,590 字符压到 4,133，降幅 95.3%，而且关键信息一条没少。这篇讲怎么做到，以及为什么不能直接截断。

## 上下文会自己长胖

刚开书时，写第 3 章要喂给模型的东西很少：世界观、一个人物卡、前一章结尾。

写到第 160 章，同样的流程，喂进去的东西变成了 8.7 万字符。拆开看构成：

| 来源 | 字符数 | 占比 |
| --- | --- | --- |
| 伏笔账（全量注入） | 78,258 | **89%** |
| 角色表（全量） | 8,516 | 10% |
| 其余（世界观 / 卷季 / 近章 / 本章要点） | 约 800 | 1% |

问题一目了然：**九成的输入给了跟本章无关的历史。**

模型不是在写这一章，是在读一本四百多条的备忘录，然后在末尾加三千字。注意力被稀释是必然的——更别说 token 成本和上下文上限。

## 根因不是"东西太多"，是"没过滤"

我原来的装配逻辑很朴素：把设定库里的东西全拼进去。

```python
for key in ("locations", "items", "events"):
    for row in bible[key]:
        lines.append(f"- {row['name']}：{row['description']}")
```

`events`（伏笔）没有按 `resolved` 过滤，没有按相关度过滤，一条不落。

讽刺的是，另一个模块在生成「状态交接文件」时是过滤的（只取未收束的）。**同一份数据，两个消费者，两套口径。** 结果就是交接文件很薄，写作上下文很厚。

这个不一致存在了很久没人发现，因为两边单独看都"合理"。

## 预算怎么分

现在装配前先定预算，写成常量：

| 层 | 预算（字符） | 内容 |
| --- | --- | --- |
| static | 4,000 | 世界观 5 段 / 力量体系 / 禁词 / 姓名红线 / 角色卡 6 张 |
| arc | 1,200 | 本卷主线 / 本季主线 / 季末钩子 |
| window | 3,500 | 近 3 章摘要 + 上一章末 900 字 + 本章要点 |
| state | 2,500 | 主角面板 / 物品栏 / 活跃 NPC 5 / 相关伏笔 12 |
| beats | 800 | 本章节拍表 |
| **合计** | **12,000** | 硬上限 |

12,000 字符约合 7.5k tokens。给正文输出（3000+ 字）留足空间之后，这个数是安全的。

**为什么是这五层而不是别的切法？** 因为这五层对应五种不同的"遗忘方式"：

- static 忘了 → 设定崩（写出表外境界、改主角性格）
- arc 忘了 → 跑题（这一卷的主线被丢下）
- window 忘了 → 断裂（上一章停在门口，这一章人在城外）
- state 忘了 → 吃书（伤好了、钥匙飞回来了）
- beats 忘了 → 节奏失控（一章跑完三章的剧情）

漏哪层出哪类错，所以五层都必须有配额，不能"总量控制"了事。

## 超了怎么办：分级降级

只在总量超预算时才降，一次降一档，降完重算：

| 档 | 动作 |
| --- | --- |
| T1 | 伏笔 12 → 8 条 |
| T2 | 活跃 NPC 5 → 3 人 |
| T3 | 世界观 5 → 4 段 |
| T4 | 近章摘要 3 → 2 条 |
| T5 | 伏笔 8 → 5 条 |
| T6 | 世界观 4 → 3 段 |
| T7 | 角色卡 6 → 3 张，伏笔描述 48 → 32 字 |

顺序是有讲究的：**先降"少一条也不致命"的**（伏笔条数、NPC 数量），**后降"少一个就崩"的**（角色卡、世界观主干）。

阶梯走完还超，才按各层自己的配额硬裁——而且裁在句读处，不留半句。

## 降级必须可见

这是我认为最重要的一条工程约束：**不许静默丢内容。**

装配器返回的不只是文本，还有一份报告：

```json
{
  "total": 4133,
  "cap": 12000,
  "tier": 0,
  "tier_label": "T0 满配",
  "sections": { "static": 1675, "arc": 0, "window": 1308, "state": 925, "beats": 225 },
  "over_cap": false
}
```

`tier` 告诉你降到了第几档，`sections` 告诉你每层用了多少。看到 `T5` 就知道这一章的伏笔只给了 5 条——**这是提醒你考虑收线，不是无声地把线索藏起来。**

如果只返回文本，作者永远不知道「为什么这章写得有点飘」——因为真正的原因可能是三条伏笔被裁掉了。

## 为什么不能直接截断

最省事的做法是 `text[:12000]`。这样一定不超预算，但会出三种事故：

1. **截在中间**，最后一句是半截的，模型会把它当完整句子理解；
2. **截掉末尾**，而末尾恰恰是本章要点和节拍表——最该保留的部分；
3. **随机性丢失**，同样超预算，今天截掉角色表、明天截掉伏笔，行为不可复现。

所以必须「分层配额 + 按句读裁剪 + 降级阶梯」，而不是一刀切。

## 实测结果

用一本 160 章规模的连载档案做只读基准（数据已脱敏，只保留结构与量级），装配下一章：

| | 旧做法 | 现在 |
| --- | --- | --- |
| 总字符 | 87,590 | **4,133** |
| 压缩比 | — | **4.7%** |
| 降幅 | — | **95.3%** |
| 降级档位 | — | T0（未触发） |
| 伏笔注入 | 400+ 条全量 | 12 条按相关度 |

分层明细：static 1,675 / arc 0（该章已超出原卷区间）/ window 1,308 / state 925 / beats 225。

省下来的 95% 不是靠"少给点信息"，而是靠三件事：

1. **已兑现的伏笔不注入**——全量账里约四成已收线，直接排除；
2. **未到期且不相关的只留名字级摘要**——单条描述从 181 字压到 48 字；
3. **全量账一条不删**——留在 `state.json` 里供查询，只是不进每章上下文。

一句话：**上下文是投影，不是账本。** 把账本塞进上下文，是长篇后期注意力涣散和成本失控的共同来源。

## 一个可测性问题

预算做完了，怎么验证降级真的生效？

小规模的书写到死也碰不到 12,000 上限——测不出来。所以装配器加了 `--cap` 参数：

```bash
python huixie.py assemble 某书 2 --cap 2000 --json
```

把上限压到 2,000，塞 60 条伏笔，就能稳定触发降级，并断言三件事：总量不超、档位确实降了、已收束的伏笔没进上下文。

**给功能留一个「可被注入的参数」，比事后手工造大数据省太多时间。** 这也是下一篇的主题：[给 AI 工作流写测试](06-huixie-testable-workflow.md)。
