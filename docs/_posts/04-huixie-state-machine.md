# 04 长篇小说的状态机：静态设定与动态状态分离

> 连载写到中后期，模型开始记错事。查下来不是记性差，是**状态没有唯一出口**。

## 症状

先看几个典型错误，写过长篇的都眼熟：

- 第 40 章左臂骨折，第 46 章他双手抱起箱子；
- 第 12 章钥匙交给别人了，第 70 章又从兜里摸出来；
- 前文说「铺子在巷子第四个门」，后文写成「第七个」；
- 第 21 章该兑现的伏笔，到第 60 章还没人提；
- 同一个配角的身份，三个版本。

这些错误有个共同点：**不是文笔问题，是数据不一致问题。**

我会写代码，所以第一反应是查数据源。查完发现问题很直白：写第 100 章时，作者（或模型）需要知道的状态，散落在五个地方。

| 状态 | 存在哪 |
| --- | --- |
| 故事内时间 | 前几章摘要里，半隐半现 |
| 主角伤势 / 修为 / 所在 | 人物设定卡，写章时不一定更新 |
| 手上有什么、欠谁人情 | 正文里，得翻 |
| 哪条线该收了 | 另一份伏笔账本 |
| 作者拍板「不许写」的事 | 脑子，或者聊天记录 |

**每写一章，要把这五处重新拼一次。拼一次错一次的概率不高，拼一百次就一定错。**

## 所以分三层

徽写的做法是把「设定」和「状态」彻底分开——它们的**变化频率差了两个数量级**，混在一起就必然互相污染。

| 层 | 文件 | 变化频率 | 谁写 |
| --- | --- | --- | --- |
| 静态设定 | `novel.json`、`bible.json` | 基本不变，一季改一次 | 人确认后手改 |
| 动态状态 | `state.json` | **每章都变** | 程序增量写回 |
| 生成视图 | `ctx-NNN.md`、接续包 | 每章重新生成 | 程序渲染 |

关键约束：**`state.json` 是写作时唯一可信的「此刻世界」**。视图是投影，不是真相源；摘要、正文、记忆都可能过期。

## state.json 长什么样

```json
{
  "chapter": 163,
  "timeline": { "now": "第163章末", "time_of_day": "深夜", "weather": "梅雨" },
  "protagonist": {
    "name": "主角",
    "condition": "左臂旧伤未愈",
    "location": "丁字巷香烛铺",
    "known": ["电表不走电", "钟声来自地下"]
  },
  "inventory": [
    { "name": "铜钥匙", "qty": 1, "held": true, "note": "第3章所得" }
  ],
  "npcs": [
    { "name": "周砚", "relation": "房东", "warmth": "戒备", "last_seen": 162 }
  ],
  "threads": [
    { "id": 12, "name": "电表不走电", "status": "open",
      "planted": 1, "due": 21, "note": "灯亮整夜，度数不动" }
  ],
  "must_not": ["本卷不许透露父亲身份"],
  "_applied": [1, 2, 3, "…"]
}
```

几个字段值得单独说：

**`known`（主角已知信息）** 是最容易被忽略、又最容易吃书的。它和「读者知道什么」不是一回事——写悬疑时，主角知道得太早，戏就没了；知道得太晚，读者会觉得他蠢。把它显式记下来，写之前先看一眼。

**`must_not`（作者拍板的禁区）** 是给作者的保险栓。我在这里写「本卷不许透露父亲身份」，下一章的上下文就会带上这句，模型不会自作聪明揭底。

**`_applied`（已写回章号）** 是幂等的实现：同一章重复跑写回，直接跳过。没有它，一次误操作就能把伏笔账记两遍。

## 伏笔为什么要四个状态

这是整个设计里改动最大的一处。

最初我用最直觉的方案：一个布尔位。

```json
{ "name": "电表不走电", "resolved": false }
```

跑到 160 章，账本上有四百多条，其中一半以上还是 `resolved: false`。问题立刻出来了：

- 有的是**真的还没写**；
- 有的是**作者拍板不写了**（读者早忘了，硬收反而难看）；
- 有的是**暂时搁置**（这卷不用，下卷要用）；
- 还有的是**已经兑现但忘了标**。

这四类混在一个 `false` 里，后果是：伏笔池永远清不干净，每章注入的上下文里塞满「其实已经作废」的条目，真正该兑的那条反而被挤掉。

改成四态：

| status | 含义 | 会不会进上下文 |
| --- | --- | --- |
| `open` | 活的，等兑现 | 会，按相关度排序 |
| `dormant` | 休眠，暂时不推 | 会，但降权 |
| `resolved` | 已兑现 | **不会** |
| `abandoned` | 作者拍板不写 | **不会** |

配套两条纪律：

**一、推进不等于兑现。**

只是提到、只是加压、只是暗示，一律记 `advance`，不改状态。只有正文里出现了「能指认的一句话」，才允许 `resolve`，并且必须把那句话作为 evidence 写进去：

```json
{ "id": 12, "evidence": "第21章 手机整夜循环播放，早上电量一格没掉" }
```

这条纪律的价值在事后：终检时不用重读全书，只看 evidence 能不能对上原文。

**二、放弃必须由作者拍板。**

程序不能自己判「这条线算了」。`abandoned` 只能人来标，且要写理由。否则模型会在某次「优化」里悄悄丢掉一条重要伏笔，而且没人知道。

> 把内部状态写进文本（比如往描述末尾追加「【开放留白·作者拍板】」）是行不通的——那是**字符串**，不是**状态**，既不能统计也不能过滤。状态必须是结构化字段。

## 相关度：不是按时间顺序取

有了四态还不够。四百多条全 `open` 的账本，一章也塞不下。

所以注入前要排序。徽写用的是一套很朴素的打分：

| 条件 | 加分 |
| --- | --- |
| 已到期（`due <= 当前章`） | +120 |
| 三章内到期 | +90 |
| 名字出现在本章要点里 | +60 |
| `related_chapters` 含当前章 | +40 |
| 近 20 章内埋下 | +25 |
| 状态是 `dormant` | −30 |
| `resolved` / `abandoned` | 直接排除 |

分数相同按 id 倒序（近埋的线通常更该管）。

这套规则能成立，前提是每条伏笔有 `planted`（埋于第几章）和 `due`（建议兑于第几章）。`due` 允许不准——它只是**建议**，写不准就留空，总比乱填强。

效果：一本四百多条伏笔的档案，单章只注入 **12 条**，其中标星的是本章该兑的。

## 写回：一章结束后的四类增量

正文过闸之后，跑一次提取，把本章发生的变化写回状态。只有四类：

```json
{
  "protagonist": { "condition": "左臂骨折", "known_add": ["钟声来自地下"] },
  "items": [{ "name": "铜钥匙", "delta": -1, "note": "交给房东" }],
  "npcs": [{ "name": "周砚", "warmth": "戒备→试探", "last_seen": 164 }],
  "threads_new": [{ "name": "地下有房间", "due": 175 }]
}
```

三条实现原则：

1. **增量合并，不做整体替换。** 按姓名或 id 更新，不会抹掉既有条目。
2. **幂等。** 章号进 `_applied`，重复跑跳过；要覆盖必须显式 `--force`。
3. **不臆造。** 正文没写的变化，一条都不许写。宁可少记，不许编。

物品用 `delta` 而不是绝对值，是因为「消耗」比「剩余」更贴近写作直觉。写「用掉一支蜡烛」比写「还剩两支」安全——后者要求作者记住上次的数，前者只要求记住这次做了什么。

## 一个反直觉的取舍

`state.json` 越大，上下文越难压进预算。所以它必须像**贴在墙上的便签**，不能像一本账。

我的划分：

- 进 `state.json`：此刻的、会影响下一章写法的（伤势、所在、手上有什么、该收的线）；
- 不进：世界观、人物出身（静态，进 `bible.json`）；整章摘要（进 `chapters.json`）；大纲与未来剧情（进 `outline.json`）。

这条线划错，两个后果同时出现：上下文变胖，而且真正该看的被淹没。
