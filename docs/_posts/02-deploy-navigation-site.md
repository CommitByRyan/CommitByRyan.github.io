## 🧗‍♂️ 核心闯关：从“难堪”到“豁然开朗”的四幕剧

如果只是顺利运行，那毫无价值。真正让我成长的，是下面这四个把我“按在地上摩擦”，又让我“爬起来通关”的问题。

### **第一幕：环境迷雾 —— 当世界对你关了门**

*   **剧情**：兴致勃勃打开终端，`npm create vue@latest` 却一直卡住，或者 `git` 被识别成陌生指令。
*   **内心OS**：“出师未捷身先死？连门都进不去？”
*   **破局关键**：从抱怨环境，切换到**主动寻找工具**。我意识到，稳定的开发环境是默认不会存在的，需要自己搭建。
*   **我的方案**：
    1.  **网络层**：使用 **Watt Toolkit**，为GitHub和NPM生态开启“绿色通道”。
    2.  **工具层**：重新安装官方Git，并执行 `git config --global user.name “Your Name”` 这行看似简单却至关重要的命令。
*   **收获的心法**：**环境是第一位生产力**。磨刀不误砍柴工，所有“玄学”问题，首先检查基础环境。

### **第二幕：部署鬼打墙 —— 那个让我最“难堪”的空白页**

*   **剧情（高潮）**：本地 `npm run dev` 一切完美，但 `git push` 部署后，打开的页面一片空白。控制台鲜红的 `404` 错误，指着我的 `main.js` 和 `style.css` 文件。
*   **内心OS**：“为什么？明明都传上去了！难道是GitHub Pages的问题？” 这是我**最沮丧的时刻**，感觉努力一拳打在了棉花上。
*   **破局关键**：我停下来，开始对比。本地打开的路径是 `http://localhost:5173/`，而线上是 `https://commitbyryan.github.io/Ryan-links/`。关键就在于这个子路径 **`/Ryan-links/`**。
    
    *   **顿悟时刻**：Vite默认构建时，所有资源路径都是绝对路径，如 `/assets/xxx.js`。这意味着浏览器会在 `https://commitbyryan.github.io/assets/xxx.js` 去找文件，当然找不到！因为它实际在 `https://commitbyryan.github.io/Ryan-links/assets/xxx.js`。
*   **我的方案**：在 `vite.config.js` 中，加入那行“神圣”的配置：
    ```javascript
    export default defineConfig({
      base: './', // 告诉Vite：请生成所有相对路径，让我能适配任何子目录
    })
    ```
*   **收获的心法**：**部署不等于上传**。你必须理解你的构建产物是如何被组织和访问的。`base: ‘./‘` 这行代码，是我对**静态资源路径**认知的毕业证书。

### **第三幕：神秘报错 —— `_plugin-vue_export-helper` 的幽灵**

*   **剧情（反转）**：路径问题解决后，页面出现了，但控制台依然飘着一个刺眼的404，追查到一个名字古怪的文件：`_plugin-vue_export-helper-xxxxxx.js`。
*   **内心OS**：“还有完没完？这又是什么Vue内部魔法？”
*   **破局关键**：我意识到，这是Vue编译器在尝试进行“静态提升”优化时产生的辅助函数。在某些部署环境下，这个动态生成的文件名可能无法被正确捕获。
*   **我的方案**：既然它由优化产生，那我可以选择暂时关闭这个优化。在 `vite.config.js` 的Vue插件配置中：
    ```javascript
    export default defineConfig({
      plugins: [
        vue({
          template: {
            compilerOptions: {
              hoistStatic: false // 关闭静态提升，从源头杜绝幽灵文件
            }
          }
        })
      ],
      base: './',
    })
    ```
*   **收获的心法**：**框架是工具，不是黑盒**。当遇到框架层面的诡异问题时，不要惧怕深入其配置项。`compilerOptions` 就是我与Vue编译器对话的窗口。

### **第四幕：学会妥协 —— 与CORS警告和解**

*   **剧情**：所有功能正常，但控制台仍有关于 `avatars.githubusercontent.com` 的CORS预检警告。
*   **内心OS**：“这警告看着真难受，要不要解决？怎么解决？”
*   **破局关键**：我评估了解决成本（可能需要自建图片代理或下载所有头像）与收益（对用户零影响）。这是一个**典型的“非阻塞问题”**。
*   **我的方案**：**记录此问题，然后放过它**。在项目README或TODO列表里记一笔“未来优化：内化头像资源”，然后全身心投入到更重要的功能开发中。
*   **收获的心法**：**工程师的时间是稀缺资源**。辨别问题的优先级，与不影响核心体验的“瑕疵”共存，是走向成熟的关键一步。完美主义是成功的敌人。
