# 06 给 AI 工作流写测试

> 最危险的不是脚本报错，是脚本报错时被判成「通过」。

## 一个真实的 fail-open

写作流水线里有个质量闸门：一段脚本检查正文的字数、禁词、重复句，不合格就拦住，不许锁章。

上层调用它时，判定逻辑是这样写的：

```python
code, out = run([CHAPTER_CHECK, ...])
if "❌" in out or "不可交付" in out:
    fail("闸门未过")
```

看起来没问题：脚本失败时会打印 `❌ 不可交付`，这里就能捕获。

但闸门脚本在**自身异常**时走的是另一条路：

```python
raise SystemExit(f"[错误] 找不到第 {n} 章")
```

退出码 1，输出里**没有 ❌**。

于是：找不到章节 → 判定为「通过」→ 继续落库、继续锁章。

`code` 明明已经拿到了，却没人用。这就是 fail-open：**该拦住的时候放行，而且不留痕迹。**

## 第二处：正则解析人类可读文本

同一个函数里还有字数硬闸：

```python
m = re.search(r"(\d+)\s*字\s*/\s*目标\s*(\d+)（(\d+)%）", out)
pct = int(m.group(3)) if m else None
if pct is not None and pct < min_pct:
    fail(...)
```

只要上面那行输出改一个字（加个空格、换个括号），`pct` 就恒为 `None`，**字数硬闸永久失效，且没有任何告警**。

这种 bug 特别阴险：代码没报错、测试没红、日志显示「闸门通过」。你只有在某章明显偏短却照样过审时，才会怀疑。

## 修法：让接口是结构，不是文本

改完之后的闸门只有一个契约：

```
退出码 0  → 通过
退出码 1  → 有硬伤
退出码 2  → 闸门自身异常
```

同时输出结构化 JSON：

```json
{
  "ok": false,
  "chapter_words": { "read": 3120, "cjk": 2310, "target": 3400, "pct": 92 },
  "fail": ["word_count: 3120 字，占 92%（<95%）"],
  "warn": ["ai_flavor_L1: 套话核心 2 处：不禁×1、微微×1"],
  "checks": [{ "id": "word_count", "level": "fail", "detail": "…" }]
}
```

上层不再读文本：

```python
r = run_json(GATE, ...)          # 解析失败直接抛
if r["returncode"] != 0:          # 0 才算通过，1 和 2 都拦
    fail(r.get("fail") or r.get("error"))
```

三条规则：

1. **判定只看退出码与结构化字段**，人类可读文本只用于展示；
2. **异常必须显式失败**——捕获所有异常，输出 `{"ok": false, "error": "..."}`，退出码 2；
3. **上层把 1 和 2 一视同仁**，不允许出现「解析不到就当通过」。

## 测试要重点测失败路径

正常路径的测试很好写，也最容易自我安慰。真正会出事的是异常路径，所以端到端测试里，失败用例比成功用例多：

```python
# 好稿：应通过
run("gate.py", slug, 1, "--file", good, expect=0)

# 坏稿：套话 + 字数不足，应拦下
r = run("gate.py", slug, 1, "--file", bad, expect=1)
assert r.json["ok"] is False
assert any("ai_flavor" in f for f in r.json["fail"])

# 缺文件：必须退出码 2，且 ok=false —— 这条是防 fail-open 的回归测试
r = run("gate.py", slug, 99, expect=2)
assert '"ok": false' in r.stdout
```

最后那条不是测"能不能找到文件"，是测**「找不到文件时不会静默放行」**。这个断言存在的意义，就是把前面那个 bug 永久钉住。

## 41 项断言，覆盖三类容易坏的地方

端到端测试在临时目录里跑完整链路，断言分三类：

**一、正向能力**

```
init → beats → assemble → gate → writeback → publish → lint → export
```

每一步都校验产出物存在且内容正确：纯净 txt 不含标题与作者有话说、md 有 front matter、manifest 字数对得上。

**二、反向拦截**

- 只有 2 个节点的节拍表 → 必须拒绝（会变成流水账）
- 缺节拍表直接装配 → 必须拒绝（防止无细纲生成）
- 坏稿 → 必须拦下
- 缺文件 → 退出码 2

**三、状态正确性**

- 写回后 `state.chapter` 推进、伏笔入库、物品增减
- 同一章重复写回 → 必须跳过（幂等）
- 已兑现的伏笔 → 不得进上下文
- 塞 60 条伏笔并压到 2,000 上限 → 总量不超、档位确实降了、条数确实变少

第三类最难写，也最有价值。它们测的不是"函数返回了什么"，而是**"重复执行、异常输入、极端数据下系统还对不对"**。

## 品牌门禁：让机器替我盯一个我记不住的约束

我做过一个品牌更名，要求全库不再出现旧名。靠人眼查不现实——几十个文件、几百处引用。

所以把这条约束写进自检脚本：

```python
FORBIDDEN = ["旧" + "名", "old" + "name"]   # 按片段拼装，避免脚本自身命中

def check_branding():
    hits = []
    for f in repo.rglob("*.md"):
        for tok in FORBIDDEN:
            if tok in f.read_text(encoding="utf-8"):
                hits.append(f"{f} 含「{tok}」")
    return hits
```

注意那个拼接：如果直接写字面量，脚本本身就是"违规文件"，自检永远不可能通过。这类自指陷阱很常见（`.gitignore` 忽略 `.gitignore` 的变体问题）。

**第一次运行，它抓出了我自己三处泄漏**——示例人名、模板里的占位人物。人眼检查时我漏了两遍。

这就是机器校验的价值：不是它比我聪明，是它**不会因为"这处我改过了"而跳过**。

## 一条被低估的经验：给功能留注入点

「降级到 T5 时行为正确吗」这件事，用正常数据测不出来——小书永远碰不到 12,000 上限。

所以装配器加了 `--cap`：

```bash
python huixie.py assemble 某书 2 --cap 2000 --json
```

上限压到 2,000，配 60 条伏笔，降级阶梯必然触发，断言就能稳定复现。

**如果你的功能有默认阈值，一定要让它可注入。** 否则测试只能靠"造一个刚好越过阈值的数据集"，既脆弱又慢。

## 教训清单

写这类工作流一年多，沉淀下来的几条：

| 原则 | 对应的事故 |
| --- | --- |
| 判定看退出码，不看输出文本 | 闸门异常被判成通过 |
| 异常也必须显式失败 | 脚本崩溃 = 静默放行 |
| 别用正则解析人类可读日志 | 字数硬闸永久失效且无告警 |
| 失败用例要多于成功用例 | 正常路径永远测不出 fail-open |
| 约束写成机器检查 | 品牌残留靠人眼漏了两遍 |
| 阈值参数化 | 降级逻辑无法验证 |
| 自检脚本避免自指 | 禁用词表里写了禁用词 |

最后一条补充：**自检脚本要能跑在干净环境里**。我在验证「别人 clone 下来能不能一模一样地跑」时，才发现三个依赖：写死的 Python 版本路径、Windows cp936 下中文输出会崩、CRLF 检出导致校验和变化。

修完这三条，才算真的"可复现"——不是在我机器上能跑。
